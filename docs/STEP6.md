# Klipr Step 6 - first end-to-end path (built 2026-11-04)

Status: BUILT and acceptance-tested against the managed Supabase DB.
Spec approved 2026-11-04 (docs/KLIPR-1A-LITE-SPEC.md, Step 6 section).
This report does not change the approved spec; it records what was built.

## What was built

- Per-user tokens, not the admin token, for library operations:
  app/user_auth.py, token hash file .klipr_user_tokens (mode 600, gitignored,
  never committed). Server resolves user_id/is_admin from the token only,
  never from client input. Step 6 endpoints reject the admin token and
  reject admin write to another user's private assets.
- Session context: app/step6.py set_user_context, transaction-local
  SET LOCAL app.current_user_id / app.is_admin. Legacy Phase 0 routes
  still allow admin (audit) or user (own rows). Queue enqueue now takes
  is_admin and sets user context when False; worker queue operations
  still use admin, render data writes use the job owner's user context.
- Upload: POST /assets, JSON with brand_id, kind, category, source_origin,
  production_method, filename, content_base64. Stores the file via
  LocalStorage, hashes SHA-256, creates an asset quarantined. Archived
  duplicate hash for the same user+brand reactivates that ID to
  quarantined instead of creating a duplicate row (import path).
- Activate: POST /assets/<id>/activate, quarantined/archived to active.
  Tattoo gate, provenance combos, and duplicate active hash are enforced
  by DB CHECKs/unique index, with server pre-checks for clearer errors.
  Only status changes on activate; provenance fields are never updated
  by this endpoint, so the immutability trigger is not bypassed.
- Projects: POST /projects, brand_id, blueprint (all 7 keys required:
  hook_type, first_frame, shot_list, length, cta, music, recipe_name),
  asset_ids planned. Writes projects + project_assets.
- Render: POST /projects/<id>/render enqueues kind render_photo_motion.
  Worker (app/worker.py) loads the project, filters planned assets to
  active only, requires 3-6 active photo assets, renders with
  VideoAdapter.photo_motion_multi (ffmpeg zoompan per photo, concat,
  1080x1920, faststart, no generative model), then in ONE transaction
  writes: finished asset (assembled, source_origin NULL), renders row,
  asset_usage rows (rendered, with duration), and origin_composition
  computed from rendered usage rows only. Planned-but-cut assets are
  excluded from composition. Blueprint is frozen once a project has a
  completed render; a second render returns 409.
- Posted / metrics / inquiries: POST /external_posts (cta_keyword unique
  per brand, posted_by manual/muse/api), POST /metric_snapshots,
  POST /inquiries, GET /weekly_report?brand_id=<uuid> (per post latest
  snapshot + inquiries by CTA, vs brand median via percentile_cont).
- Reads: GET /assets, /projects, /renders, /external_posts, all user-scoped.

## Known limitations, honestly stated

- Session variables are freely settable by a party holding application-role
  SQL execution; full prevention needs per-user Postgres auth or a
  function-only layer, both deferred per spec. API-level isolation is
  proven by the second-user test above; DB-level impersonation by a SQL
  holder is not prevented by this build.
- Brand ownership on assets is enforced in server code (brand must belong
  to the token user) plus RLS on user_id; a composite DB FK for brand
  ownership is not in the 29-table schema.
- Render handles photo assets only in Step 6; video_clip assets fail
  the render job with a clear error, they are not auto-converted.
- No real Shyftd.ink video has been rendered or posted yet. That still
  needs Matt's 3-6 real assets + blueprint, a Matt operator user + brand
  in the managed DB, and Matt posting manually. The test render above
  was solid-color test images, not publishable content.
- Storage is local disk in this proof, not S3. S3 driver remains a stub.
- Off-VM daily backup schedule is still not running; see BACKUP-SCHEDULE.md.
